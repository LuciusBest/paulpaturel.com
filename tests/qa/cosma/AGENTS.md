# AGENTS.md

Guidelines for agents (and contributors) working in this repository. Keep changes small, explicit, and respectful of the existing stack: static HTML/CSS/vanilla JS with no build step.

**Scope**
- Applies to the entire repo unless a subdirectory adds its own AGENTS.md.
- Follow direct user instructions over these guidelines if they conflict.

**Repo Map (common paths)**
- `src/index.html` — main entry point copied to `public/` during build.
- `src/css/` — site styles (`style.css`, `projectsLayout.css`, `ui.css`, `fonts.css`).
- `src/js/` — vanilla JS modules grouped by domain (`global/`, `media/`, `overlay/`, `projects/`, `ui/`, `data/`).
- `src/font/` — local fonts used by the site.
- `src/data/` — JSON content served to the frontend (`projectTexts.json`).
- `public/` — build output generated by `npm run build` (do not edit directly).
- `tests/qa/cosma/` — QA scripts and artifacts (never include from production bundles).
- `redirects.csv`, `src/.htaccess` — redirect manifest and Apache rules.

**Ground Rules**
- Keep it static: no frameworks, bundlers, or servers unless explicitly requested.
- Minimal, surgical diffs that solve the stated task. Do not refactor unrelated code.
- Maintain cross‑browser compatibility (latest Chrome/Firefox/Safari, iOS Safari, Edge).
- Default to progressive enhancement; do not break behavior without JS.
- Place new files in the appropriate folder (`css/`, `js/`, `img/`, `font/`).

**HTML**
- Use semantic elements (`header`, `nav`, `main`, `section`, `article`, `footer`).
- Prefer link/script ordering: CSS in `<head>`, JS at end of `<body>` or with `defer`.
- Avoid inline JS and inline styles; keep behavior/style in `js/` and `css/`.
- Keep IDs unique; prefer classes for styling and JS hooks (`data-*` when appropriate).

**CSS**
- Plain CSS only; keep selectors simple, avoid over‑specificity and `!important`.
- Co-locate new styles in an existing file when related; otherwise create a focused new file and include it in `index.html`.
- Naming: readable, hyphenated class names; group by component/feature. BEM is fine but not required.
- Fonts: prefer `font-display: swap;` when touching font-face rules to improve rendering.
- Respect reduced motion: use `@media (prefers-reduced-motion: reduce)` for animations.

**JavaScript**
- Vanilla JS. Avoid external deps. No bundling.
- Wrap feature code to avoid leaking globals. Use `DOMContentLoaded` or `defer`.
- Defensive DOM querying; guard against missing elements.
- Do not block scroll/keyboard navigation unless required. Coordinate with `axis_lock_scroll.js` if changing scroll behavior.
- Keep modules focused: one feature per file. Reuse utilities where possible.

**Data and Content**
- `data/projectTexts.json`: preserve schema and keys when updating. Validate JSON.
- Images/assets: optimize (reasonable size), use descriptive filenames, include `alt` text in HTML.

**Accessibility (a11y)**
- Ensure color contrast meets WCAG AA.
- Keyboard navigable: focus styles visible; no keyboard traps.
- Provide ARIA labels/roles only when semantics are insufficient.
- Respect `prefers-reduced-motion` and reduce parallax/animations accordingly.

**Performance**
- Defer non‑critical JS; avoid heavy synchronous work on load.
- Lazy‑load large media when appropriate.
- Reuse existing fonts; do not add new font files without need.

**SEO**
- Keep `title`, `meta description`, and Open Graph tags accurate per page.
- Update `sitemap.xml` when adding/removing top‑level pages.
- Keep `robots.txt` consistent with intended crawlability.

**Security**
- No third‑party scripts without approval. If added, document source and integrity.
- Avoid inline event handlers. Prefer delegated listeners in JS files.

**Deployment**
- Assume static hosting via cPanel. No build step expected; keep paths relative.
- If adding pages/assets, ensure links are correct for case‑sensitive servers.

**Style and Formatting**
- Encoding UTF‑8, LF line endings.
- Indentation: 2 spaces in HTML/CSS/JS.
- Comment sparingly but clearly for non‑obvious logic.

**Working Practices for Agents**
- Planning: outline steps with the plan tool for multi‑step tasks.
- Small patches: prefer focused diffs and explain rationale briefly.
- File references: point to paths and line numbers in messages when relevant.
- Validation: for HTML/CSS changes, sanity‑check with validators/lint if available; for JS, test in a minimal way without introducing tooling.

**Common Tasks Checklists**
- Add a new feature (JS):
  1) Create `js/<feature>.js` with isolated logic. 2) Hook in HTML with `defer`. 3) Add minimal CSS if needed. 4) Test without errors when feature DOM is absent.
- Add new styles: 1) Extend an existing CSS file if related; else new file. 2) Avoid regressions; scan main breakpoints. 3) Respect a11y and reduced motion.
- Add a new page: 1) Duplicate base structure from `index.html`. 2) Update meta/OG. 3) Link from nav. 4) Update `sitemap.xml`.

**Project‑Specific Notes**
- `axis_lock_scroll.js`: If modifying scroll locking, ensure it doesn’t trap focus and works with touch + wheel input.
- `tags_filter.js`: Filtering should degrade gracefully; show all items if JS is unavailable or errors.
- `dynamicTextOverlay.js`: Ensure text remains readable over backgrounds; consider contrast checks.
- `tests/qa/cosma/`: Treat as dev/QA utilities; avoid including references from production pages unless requested.

**When in Doubt**
- Ask before introducing dependencies, new patterns, or broad refactors.
- Prefer clarity and maintainability over cleverness.
